# SmoothieV2 support

The SmoothieV2 simulator is experimental. It stages the supplied firmware source, builds its motion core and selected modules for the host, and runs the real firmware logic against simulated hardware. It does not yet provide all SmoothieV1 simulator features; in particular, handler coverage and race analysis are only partially observed.

## Build and run

Set `SOURCE` to the SmoothieV2 `Firmware` directory (the one containing `src`, `Hal` and `RTOS`), and optionally set `BUILD` to an output directory:

```sh
make -f Makefile.v2 SOURCE=/path/to/SmoothieV2/Firmware BUILD=build-v2
build-v2/smoothie-sim-v2 --config /path/to/config.ini --gcode /path/to/job.gcode --out result.json
```

Add `COVERAGE=1` to the build command to include compiler coverage instrumentation. When the module checker uses that simulator, it records call and line counts for recognized command-handler methods in `v2_handler_method_coverage` and recognized periodic callbacks in `v2_timer_callback_coverage` in its JSON result. Each checker invocation uses its own counters and merges extra workloads. This is partial coverage: other callback forms and complete module coverage still require further instrumentation. The checker needs compatible `gcov` and `nm` executables on its path. Coverage instrumentation can alter allocation attribution, so use a separate non-coverage build for the memory estimate.

The firmware files are staged into the build directory and the original tree is not modified. The default board is Prime; set `BOARD=NUCLEO` or `BOARD=DEVEBOX` at build time to select the corresponding firmware board defaults. These settings model the selected firmware defaults, not complete board-level electrical behavior. The simulator does not enforce the firmware's board-specific reserved-pin list, so an accepted pin assignment may still be unavailable on the physical board. Actuators without a `driver` setting are treated as external drivers, unlike the Prime firmware's default internal drivers; explicitly configured `tmc2590` and `tmc2660` drivers use the firmware's driver code and simulated SPI devices. A Trinamic actuator can be slaved to a primary actuator with a matching driver and microstep setting. `--motor-trace path` records the signed physical pulse position of each motor that stepped, keyed by its firmware motor number, including slaved motors. `--modules` enables the supported configured modules; a known enabled module that is not supported is rejected. `--blocks-in` can replace `--gcode` for block replay, and `--full-steps`, `--no-steps` and `--alloc-trace path` control step and allocation recording.

Results include `initial_steps`, the actuator counters before startup playback or workload execution. Motion checkers add the signed planned movement to these initial counters, which can be nonzero for delta and SCARA kinematics. `pulse_position` remains relative to the start of simulation.

The Trinamic model records 20-bit register writes and returns zero status. It assumes a 24 V motor supply and does not model driver faults, motor power loss, or the motor's physical response. `--spi-trace path` writes a JSON list of Trinamic register writes with their SPI channel and chip-select pin. Trinamic drivers and MAX31855 sensors require different SPI modes and must use separate simulated channels.

Undriven GPIO inputs use the firmware's default pull-up; the `v` and `^` pin modifiers select pull-down and pull-up. A pin driven by `;@sim pin` keeps that external level when its direction changes. Floating inputs retain their last simulated level; this is a deterministic approximation, not an electrical noise model.

Supported firmware modules include extrusion, endstops, Z probing, drilling cycles, button-box inputs, thermistor and MAX31855 temperature control, switches, temperature-triggered switches, motor current control, the kill button, laser control and filament detection. Button actions can queue G-code and M-code commands, including SD-card file selection, or use the firmware's direct kill and fault actions. For a button configured with `pin = external`, `;@sim button name 1` presses it and `;@sim button name 0` releases it through a simulated provider; this does not model an external hardware provider. Configure `[player]` with `on_boot_gcode_enable = false` when no simulated SD-card root is supplied; a filament switch, bulge input or missing encoder pulse can invoke the firmware suspend path. For the bulge input, the staged firmware initializes a detector pointer that the supplied firmware otherwise leaves uninitialized; this is a simulator-side correction, not a change to the original firmware. Simulated PWM tracks frequency and duty cycle rather than individual edges. The MAX31855 model supplies temperature readings and electrical sensor faults; other SPI devices and several other modules are unsupported.

The staged Z-probe firmware checks whether each selected leveling or calibration strategy exists before calling it. Without a matching strategy, the simulator reports the leveling command as unhandled; the supplied firmware otherwise dereferences a null pointer. An unknown strategy or one that fails configuration also causes simulator setup to fail, rather than continuing with an unusable strategy. These adjustments do not modify the original firmware tree.

The firmware's digital readout can drive individual or cascaded MAX7219 seven-segment displays. The simulator decodes the clock, data and chip-select pin transitions into display registers; `;@sim expect-display PD3 0 4 129` checks register 4 of device 0 on chip-select pin PD3. Poll frequencies from 1 to 100 Hz are supported. Sub-microsecond bus waits use the simulator's one-microsecond clock resolution, so display transfer timing is approximate. The staged firmware initializes the readout's default 10 Hz polling frequency when its common section is absent; the original firmware tree is unchanged. Display registers are modeled, not optical output or electrical faults.

Manual pulse generators use the firmware's quadrature decoder and command-context motion handler. Drive their configured encoder pins with `;@sim pin` transitions; shared handwheels select and disable axes with the firmware's `M922` command. Interrupt pins with the same line number cannot be used simultaneously.

The lathe module can measure spindle speed from an index input or a simulated 16-bit quadrature counter. `;@sim encoder -2` advances the counter by a signed number of counts; `;@sim encoder-after 10 -200` applies a change after 10 ms. Index input changes can be scheduled with `pin-after`. Index-based `G33` and encoder-based `G33.1` execute the firmware's motion handlers. A manual `G33.1` without a Z destination requires `;@sim stop-after 200` beforehand, which schedules a stop request after 200 ms, including for a button-queued command. The staged firmware advances simulated time in 100 µs increments while spinning for index interrupts and initializes the stop-request flag in output-stream constructors that leave it uninitialized; the original source is unchanged. In the supplied firmware, a positive-Z `G33.1` terminates without moving because its end-position condition only handles negative travel. This is observed host behavior, not a physical-board qualification.

The electronic leadscrew uses the firmware's lathe and TM1638 panel drivers. `;@sim tm-buttons 2` sets the panel's eight button bits and `;@sim expect-tm1638 0 63` checks a display RAM byte. The simulator decodes pin traffic and models panel registers and buttons, not optical output or electrical faults. Its staged panel driver advances simulated time during bus waits; the original firmware is unchanged. Software-timer callbacks run serially, with expirations deferred while a callback is active. The command thread and cooperative player wait for a held mutex until it becomes available or the requested timeout expires; the command thread advances the cooperative player and simulated time while waiting. Mutex ownership distinguishes the command thread, each player task and nested callback depth. Timer and interrupt callbacks still use nonblocking mutex acquisition, so this is not a complete FreeRTOS mutex model.

The graphical ST7920 driver can be configured with `[st7920]`, `clk` and `mosi` pins. The supplied firmware has no graphical-display application, so simulator-only directives exercise the driver directly: `;@sim graphics-init`, `;@sim graphics-pixel 0 0 1`, `;@sim graphics-refresh`, and `;@sim expect-graphics 0 0 1`. The model decodes the serial pin traffic into graphics RAM; it does not model optical output or electrical faults. The staged driver advances the simulated clock during busy waits, and sub-microsecond timing is approximate. The original firmware is unchanged.

With the player configured, a workload line `play /path/to/job.gcode` runs the firmware file player against a host file. The `-p` option starts paused; `M24` resumes, `M25` pauses and `M26` resets playback to the start. Player console commands `progress`, `abort`, `suspend` and `resume` are also dispatched to the firmware. Pass `--sd-root /path/to/directory` to map firmware `/sd/` paths into that directory for `M23`, `M32` and the configured startup file. Paths that resolve outside the directory are rejected. The firmware's `M21` card response and `M27` progress response are available. Startup playback begins before workload commands and continues cooperatively with them; the whole startup file is not guaranteed to finish first. The staged firmware waits for the aborted player task to exit before starting its replacement on `M26`; the original firmware tree is not modified. The player runs as one cooperative task using Linux user contexts, yielding at queue operations and firmware delays while the command thread services its queue. This is not a general real-time operating-system scheduler. A task still paused when the workload ends eventually fails the run instead of silently claiming completion. Firmware task delays advance simulated time and dispatch due timers. Completed player task delays are summarized in `v2_task_delays` as call counts and inclusive elapsed simulated time; time while other simulated work runs is included. They are task waits, not attributed command-handler blocking, and other task and callback delays are not covered.

The simulator records `safe_sleep` calls observed while a G-code or console command is being dispatched, with the active command and input line. This is command context rather than module attribution: timer callbacks can run during the command. The optional `v2_module_callback_counts` result records completed halt and command-context broadcasts by module group; it does not distinguish instances or include other callbacks. `v2_module_callback_elapsed_us` records their inclusive simulated elapsed time, including nested work, rather than processor time. `v2_command_callback_counts` counts completed handler invocations by command, including handlers that return without processing it. `v2_handler_callback_counts` groups those invocations by the declaring class where recognizable from the bound callback type, otherwise under `unattributed`; it does not identify the method or instance. `v2_handler_method_counts` includes zero counts for registered methods recognized from direct `std::bind` forms and defined in the same source file, and for recognized static handlers defined in another file, then counts their entries. It also counts direct calls to those methods, and other registrations can be missed. `v2_handler_method_elapsed_us` records total and maximum inclusive elapsed simulated time for these method entries. This includes timer callbacks and waits occurring inside the method, and does not measure processor execution time. `v2_timer_callback_counts` counts named callbacks registered in the recognized direct ticker-call forms; other timer registrations may be missed. `v2_timer_callback_elapsed_us` similarly records inclusive simulated time for recognized periodic callbacks; it includes time spent in nested work and does not measure processor time. These observations do not cover all waits, handler execution time or module coverage. The `thermistors` console command lists the firmware's predefined thermistors when temperature control is enabled.

G-code workloads can use `;@sim pulses PD2 3` to invoke three rising-edge callbacks on an allocated interrupt pin without changing its physical level or advancing time. The pin must have a rising-edge or change interrupt, even for zero pulses. Workloads can also use `;@sim pin PA0 1` to set an allocated input pin, `;@sim pin-after 500 PA0 0` to schedule a physical pin level change after 500 ms of simulated time, and `;@sim wait 1000` to advance time by 1000 ms. `;@sim expect-pin PD1 1` checks an allocated pin's physical level and fails the run if it differs. `;@sim expect-pwm PWM1_1 0.5` checks an allocated hardware PWM output's duty fraction, with a tolerance of 0.0001. `--adc-value 200` sets the initial reading for all thermistors; `;@sim adc 200` changes them during a workload, while `;@sim adc ADC1_0 200` sets one allocated channel. ADC readings use the 12-bit range 0 to 4095. Thermistors use distinct `ADC1_0` through `ADC1_6` names. `;@sim thermocouple PD2 250` sets the temperature in °C of the MAX31855 configured with chip select `PD2`; its initial value is 25 °C. Use `open`, `short-gnd` or `short-vcc` instead of a temperature to simulate an electrical fault; setting a temperature clears the fault. These directives are simulator inputs, not firmware commands.

The [checker reference](checkers.md) describes STM32 memory and firmware-size analysis. Simulator results are host observations and do not establish physical-board behavior.

## Interrupt exploration

`--race-force-every N` injects a step interrupt at every Nth checkpoint before the planner writes a maximum rate and immediately before or after it locks a block. At exit, `SIM_V2_RACE` on standard error reports the number of checkpoints and injected interrupts, how often an interrupt started the block being replanned (`target_started`), how often the planner reached its protected updates while that block was ticking, and how often it wrote the maximum rate while the block was ticking. The latter is an observed interleaving, not by itself proof that a step interrupt consumes that field. A zero `target_started` means the requested interleaving was not observed. The injected interrupts do not advance simulated time; this explores selected interleavings and is not cycle-accurate timing or a comprehensive race analysis. It does not check every field touched by the planner.

The same option also injects a step interrupt between the read and write of each Nth command-context conveyor flag update. The model treats the firmware's conveyor bitfields as one shared byte. `conveyor_flag_writes` counts eligible updates, `conveyor_flag_interrupts` counts injected interrupts, and `conveyor_lost_stores` counts writes that overwrite a different bit changed by the interrupt. A zero lost-store count only covers the exercised workload and interleavings. The shared-byte layout and host interleavings are a model, not a measurement of physical-board execution.

Alternatively, `--race-window-us W` injects a step interrupt at those checkpoints when its next timer event is within W microseconds. The scheduled step is consumed without advancing the clock; a pending pulse-clear event that comes first prevents the injection. Other scheduled callbacks can still be reordered, and the window is an interleaving approximation rather than interrupt latency. Both race options can be combined.

## Run the experimental checks

```sh
./run_checks_v2.sh build-v2/smoothie-sim-v2 /path/to/SmoothieV2/Firmware - out-v2
```

This runs the motion, module-interference and temperature-fault checks using a small included Cartesian configuration, and writes `out-v2/report.html`. Complete handler self-time, blocking and coverage are reported as not measured; partial callback counts and inclusive elapsed simulated times appear in the module checker result and report. The static module scan warns when no reference tree is supplied. Set `V2_CONFIG`, `V2_MOTION` and `V2_WORKLOAD` to override the included files; the motion check assumes Cartesian kinematics, and the fault case requires a configured hotend.

Independent motion tests exercise CoreXY, CoreXZ, linear delta and equal-arm Morgan SCARA configurations. A centered rotary-delta move also checks the symmetry of all three motors. Both delta tests disable the firmware's homing requirement to isolate motion. With the supplied firmware and unequal SCARA arms of 150 mm and 100 mm, a requested X1 Y1 endpoint produced joint positions whose forward geometry gives approximately X-19.95 Y13.91; the firmware's unequal-arm inverse calculation uses the square of the first arm length in its denominator. This is a host observation, not a physical-board result; the simulator leaves the firmware calculation unchanged.

The default motion is a short linear case, not an arc test. To check the included square-and-arc workload, set `V2_MOTION=cases/cartesian/square.gcode` when running the script from the repository root. With the supplied firmware revision and the included configuration, host simulation reports out-of-order trapezoid ticks on arc blocks; the firmware's sample minimal configuration also reproduces this. In one block, rounding makes the initial rate slightly greater than the maximum rate, and a negative acceleration time is converted to an unsigned tick count. This is a host observation, not evidence of behavior on a physical board. The simulator does not correct that planner calculation.

Set `STM32_LAYOUT` to the output of `tools/stm32_memory_layout.py` to enable the memory estimate, including allocations from configured modules. When the main simulator has coverage instrumentation, set `V2_MEMORY_SIM` to a separate non-coverage simulator built from the same firmware source and configuration; the workflow does not verify that the builds match. Firmware command-handler registration allocations are marked in the trace so the estimate can retain them when compiler inlining obscures their firmware stack frames. Without a layout the report says memory was not measured. The optional fifth and sixth arguments are reference and candidate Prime ELF files for the size comparison; `SIZE_TOOL_PREFIX` selects the binutils prefix. A reference firmware tree may replace `-`, and `BASE_SIM` can point to its simulator.
